# Application Review — 27 September 2026

Second full review, after the September remediation plan was completed. Two lenses:
developer (remaining bugs) and product manager (missing features and usability
bottlenecks in the create → send → complete → analyse → plan → accredit funnel).

Four independent review passes were run (data layer, frontend logic, money/team/auth
flows, product journey). Every finding marked **[verified]** was re-checked by hand
against the current code on `main` (commit 0b2b788); the rest were traced by a
reviewer through the actual code paths cited. Nothing from REMEDIATION_PLAN.md is
repeated here. Baseline at review time: `tsc --noEmit` clean, 16/16 active tests pass.

Severity key: 🔴 breaks a core flow or loses money/trust · 🟠 wrong behaviour users will hit · 🟡 worth fixing, lower impact.

## Part 1 — Bugs (developer review)

### A. Subscriptions and payments

**A1 🔴 Abandoned checkout downgrades a paying school to free. [verified]**
`create-payment-session/index.ts:153-159` inserts a `status='pending'` subscriptions
row on *every* checkout attempt, before the user even reaches Stripe. The invoice
path does the same (`update-invoice-status/index.ts:70-80`). `get_user_subscription`
(`20260926124520_fix_critical_rls.sql:157-174`) returns only the **newest row by
created_at, with no status filter** — so the moment an active customer opens the
upgrade page and abandons checkout (Back button, timeout, second thoughts), the
pending row becomes "their subscription", `is_active=false`, and Analysis
benchmarks, Improve, Accredit and Custom Questions all lock. Nothing ever cleans
pending rows up. Fix: make `get_user_subscription` prefer active rows (or stop
pre-creating pending rows).

**A2 🔴 The cleanup that should have mitigated A1 has never worked. [verified]**
`update-invoice-status/index.ts:273-287` sets stale pending rows to `status:
'inactive'` — but the `subscription_status` enum is
`('active','canceled','expired','pending')` (`baseline.sql:155-161`). The update
errors every time and the error is deliberately swallowed.

**A3 🔴 Webhook can activate the wrong subscription row.**
`stripe-webhook/index.ts:145-156` queries existing subscriptions with no status
filter and no ORDER BY and takes `existingSubs[0]`. A re-subscriber typically has
[old cancelled row, fresh pending row]; the webhook may "activate" the old row
while the fresh pending row stays newest — so even after successful payment,
`get_user_subscription` still reports free and PaymentSuccess times out at 60s.

**A4 🔴 Re-subscribing after cancellation never re-activates.**
The `checkout.session.completed` handler (`stripe-webhook/index.ts:159-170`) never
clears an existing `end_date`. A user who cancelled (end_date set in the past) and
later re-subscribes pays, gets `status='active'` — but `get_user_subscription`
requires `end_date IS NULL OR end_date > NOW()`, so the plan never activates.

**A5 🟠 Refunds never downgrade the plan.**
The webhook handles no `charge.refunded` / dispute events, and marking an invoice
payment `refunded`/`cancelled` (`update-invoice-status/index.ts:226`) updates
payment_history but leaves the subscription active with its 3-year end_date. A
refunded school keeps full access.

**A6 🟠 Paid features are enforced in the browser only.**
All plan gates live in React pages (`Improve.tsx:57`, `Accredit.tsx:46`,
`CustomQuestions.tsx:18-20`, `Analysis.tsx:63`); RLS on action_plan_*,
accreditation and custom_questions tables checks org role, never plan, and no
edge function checks plan. Anyone comfortable with devtools can use paid features
free via the API. Data stays org-scoped, so this is a revenue issue, not a
privacy one — a plan check inside RLS (or an RPC gate) closes it.

**A7 🟡 Payment-history dedupe is dead for subscription checkouts.**
`stripe-webhook/index.ts:206-210` dedupes on `.eq('stripe_payment_id',
session.payment_intent)`, which is null in subscription mode and `eq null` matches
nothing in PostgREST — Stripe retries create duplicate payment rows. Related:
renewal payments (`invoice.paid`) are never recorded in payment_history, and that
handler's reactivation branch requires metadata the checkout never sets (dead code).

**A8 🟡 plan_type derived from the plan's display name.**
`create-payment-session/index.ts:97` does `planData.name.toLowerCase()`. Renaming a
plan row (e.g. "Premium Plan") makes the webhook insert an invalid enum after
payment → 500s → Stripe retries forever. Map explicitly or add a plan_type column.

**A9 🟡 Invoice "subscription" purchases get the same hard-coded 3-year end_date
as one-time purchases** (`update-invoice-status/index.ts:252-256` — both ternary
branches are identical). Fine if intended; flagging in case annual invoicing is meant.

### B. Survey lifecycle

**B1 🔴 "Publish Survey" / "Send Invitations" / "Save & Preview" skip validation
entirely. [verified]** Both buttons call `form.getValues()` after `e.preventDefault()`
(`SurveyForm.tsx:90-103`), so the zod schema never runs — a survey can be published
with an empty name. Compounding: **nothing validates close date ≥ survey date**, so
a survey can be published already-closed while the UI says it's live; and the date
pickers disable *today* (`SurveyFormInputs.tsx:149,189` — `date < new Date()` is
true for today-at-midnight), so users can't start a survey today.

**B2 🔴 "Copy Link" silently re-opens archived surveys and publishes drafts/scheduled
surveys early. [verified]** `SurveyList.tsx:93-118` flips any survey that isn't
Sent/Completed to `Sent` after copying — including Archived rows visible under
"Show All". An archived survey copied "for reference" starts accepting responses
again; write failures are only console-logged.

**B3 🔴 Every "Remind" click sends the reminder emails twice. [verified]**
`SurveyList.tsx:165-183` invokes `send-survey-email`, then on success calls
`onSendReminder(survey.id)` → `Surveys.tsx:238-248` → `sendSurveyReminder()`
(`sendReminder.ts:102`) which invokes the same function again. Delete one path.

**B4 🟠 Editing a live survey's questions is delete-then-reinsert with swallowed
errors.** `SurveyEditor.tsx:232-239, 303-316`: if the re-insert fails the user
still gets a success toast while respondents see a survey with no custom questions.

**B5 🟠 Close-date and analysis date-range boundary bugs.** Close date stored as
local midnight and treated exclusively (`is_survey_open`: `close_date > now()`;
`status.ts:10-13`) — the survey actually closes at the *start* of the chosen day,
losing the final day the UI implies. Analysis custom ranges compare a date-only
string against timestamps (`Analysis.tsx:110-119`, `analysisUtils.ts:111-113`),
excluding the chosen end day and shifting a day in BST.

**B6 🟠 The X that removes a selected custom question submits the whole form.**
`QuestionList.tsx:51-57` — button lacks `type="button"` inside the form; clicking
it saves the survey and opens a preview tab.

**B7 🟠 Opening the "Add Questions" modal loops refetches.**
`CustomQuestionsModal.tsx:104-110` depends on `refreshQuestions`, recreated every
render by `useCustomQuestions.ts:18-30`, and each fetch triggers another —
continuous queries while the modal is open.

**B8 🟡 Custom-question responses aren't validated against the survey. [verified]**
`submit-survey-response/index.ts:156-175` inserts with the service role and never
checks the question_id belongs to the survey — a respondent can attach answers to
arbitrary question UUIDs (data integrity, not confidentiality).

**B9 🟡 Double-submit race on the respondent form.** The button disables on submit,
but `useSurveyForm.ts` `submitForm` has no internal guard and the server has no
idempotency — a fast double-click can store two responses.

### C. Analysis correctness

**C1 🔴 Staff who answer "All the Time" to the leaving question vanish from
analysis. [verified]** The form offers five options including 'All the Time'
(`survey-form/constants.ts:21-27`), but `getLeavingContemplation`
(`analysisUtils.ts:196-211`) maps only Often/Sometimes/Rarely/Never; 'All the Time'
is dropped from counts **and** the denominator. The most at-risk staff are
invisible in the chart, the emailed report and the AI-summary input.

**C2 🔴 The "national benchmarks" schools pay for are hard-coded constants.
[verified]** `analysisUtils.ts:126,141,146` (national average always 7.8) and
:289-295/:341-346 (every question compared against a fixed 25/40/25/10 split).
The landing page and Analysis subtitle promise real comparison. Either compute
real cross-org aggregates server-side (with a minimum-N rule) or relabel as
illustrative until there's data. The dashboard "Benchmark score" tile is likewise
just the school's own average (`utils/survey/benchmark.ts`).

**C3 🟠 The 10-response minimum for the AI summary never gates anything.**
`summaryUtils.ts:58-76` reconstructs response counts from proportions that sum to
~1.0, so the check passes with a single response. And when the summary function
errors, `getMockSummary()` presents fabricated "85% of staff…" findings as real.

**C4 🟠 Dashboard survey rows link to the wrong analysis and mislabel drafts.**
`RecentSurveysList.tsx:97,150` derives status without `survey.status` (drafts show
"Sent") and links to `/analysis?surveyId=…`, but Analysis.tsx never reads the
param — it always shows the first survey.

**C5 🟡 Dashboard response rate is meaningless.** `dashboardStats.ts:77-131`
divides responses from all surveys by recipients of email surveys only — 0% or
>100% for link-distributed surveys (`countEmailResponses` is an acknowledged stub).

**C6 🟡 Stale-response races.** `Analysis.tsx:100-145` (and Surveys.tsx,
SurveyEditor.fetchSurvey) have no cancellation guard — quick survey/range switching
can leave the previous survey's charts displayed.

### D. Accounts, team, admin

**D1 🔴 "Create Organisation" always fails and leaves an orphaned org row.
[verified]** `OrganizationContext.tsx:138-168` inserts the org, then a membership —
but the only INSERT policy on organization_memberships (`om_create_org_admins`,
`baseline.sql:2178`) requires the caller to *already* be an admin of that org, and
the RPC fallback had EXECUTE revoked. Needs a SECURITY DEFINER create-org function
or a self-as-first-admin policy.

**D2 🟠 Silent no-op writes reported as success.** RLS rejects-by-filtering (0 rows,
no error), and three UI paths toast success anyway: "Leave Organization"
(`OrganizationsList.tsx:191-210`, non-admins), remove member
(`useTeamMembers.tsx:160-190`), and self-revoking platform admin
(`UsersManagement.tsx:96-103`). Conversely nothing stops the *last* admin deleting
their own membership via API, bricking the org (invites need an admin inviter).

**D3 🟠 Changing your email breaks at the confirmation step.** `send-auth-email`
sends email-change links as `type=signup` (`index.ts:51-54`); `Login.tsx:45-63`
verifies them with `verifyOtp({type:'signup'})`, which can't verify an email-change
token → "Please sign up again." (Magic-link URLs are similarly ignored if ever
enabled.)

**D4 🟠 Admin Users screen shows 0 surveys / 0 responses for everyone. [verified]**
`admin-get-users/index.ts:146-176,292-324` filters survey_templates by
`creator_id`, a column that doesn't exist; the error is absorbed and counts
default to 0. (Same mistake sync-hubspot-users had, fixed there but not here.)

**D5 🟠 Invitation errors all render as "Invitation Not Found".**
`FunctionsHttpError.message` is always the generic non-2xx string; the body is on
`error.context`, never read — so the expired / already-accepted branches in
`AcceptInvitation.tsx:46-48` never fire. Also the page tells a logged-in user with
a mismatched email "You can still accept" (`:351`) while the server returns 403.

**D6 🟡 Invitation resend 500s when an expired duplicate exists**
(`send-team-invitation-v2/index.ts:85-114`: multi-row update + `.single()`), and
the emailed role comes from the request body rather than the invitation row.

**D7 🟡 User-deletion lifecycle.** `custom_questions.creator_id → auth.users ON
DELETE CASCADE` means deleting a departed user destroys their org's questions and
all historical answers to them; meanwhile other FKs are NO ACTION so most user
deletes just fail; subscriptions/payment_history CASCADE erases financial records.
Needs a documented delete/anonymise procedure and `SET NULL` on creator columns.

**D8 🟡 Admin feedback-analytics "Refresh" spins forever**
(`useSurveyFeedbackAnalytics.tsx:152-155` sets loading, nothing refetches).

**D9 🟡 Editing only a purchase's invoice number fails** —
`usePurchaseUpdater.ts:44-52` can send no `status` key and the function requires it.

- Surveys list passes close date as a locale string, `new Date()` parses it engine-dependently — potential Safari crash (`Surveys.tsx:185-189`, `SurveyList.tsx:50-83`); pass the ISO date.

- Older edge functions still send `Access-Control-Allow-Origin: *` (harmless — they authenticate — but inconsistent with the pinned-CORS work).

## Part 2 — Product review (PM lens)

Goal: easy path from *create survey → staff complete it → actionable findings →
plan against the framework → submit for accreditation*.

### Ranked gaps

1. **The primary "Create Your First Survey" button 404s. [verified]** Four
   components navigate to `/new-survey`, which isn't in the router
   (`DashboardEmptyState.tsx:29`, `GettingStartedGuide.tsx:63`,
   `RecentSurveysList.tsx:72`, `analysis/NoDataDisplay.tsx:22`). Every brand-new
   user's first click lands on the 404 page. Minutes to fix (redirect route or
   point them at `/survey-editor`). **Highest-impact fix in the repo.**
2. **Fake national benchmarks** (= bug C2) — a paid, advertised feature showing
   invented numbers is a credibility risk for an accreditation body.
3. **No anonymity floor on results.** Charts and, worse, verbatim free-text
   answers show from the very first response, with role collected — in a small
   school the head can identify the author. Only the (broken, C3) AI-summary
   check has a threshold. Suppress results below ~5 responses and *say so on the
   survey intro* — it's also a response-rate booster.
4. **Analysis → Improve is a dead end at the funnel's most valuable hinge.**
   Nothing maps survey findings to the framework's 8 sections / 58 descriptors;
   the plan initialises as an undifferentiated 58-item to-do list. The 8 rating
   questions align almost 1:1 with the 8 sections: show each section's survey
   score in the Improve summary and link each Analysis chart to the matching tab.
5. **The post-publish "now send it" moment is muddled.** Publish navigates to the
   list while the toast says "use the shareable link below" (nothing below);
   the in-form link panel is unreachable because both buttons bypass form submit.
   Land on a "Your survey is live" screen: copy link + QR + suggested email text.
6. **No response-collection loop for link-distributed surveys** (the realistic
   majority): reminders exist only for the email-recipient path, and the response
   -rate stat ignores link respondents (C5). Ask for expected staff headcount at
   creation; drive response-rate and a "nudge your staff" prompt from it.
7. **The accreditation reward moment is missing.** No email when a submission is
   approved/rejected (school only finds out by revisiting), and "Download
   Certificate" is a stub that toasts success and does nothing
   (`Accredit.tsx:158-170`). Send a decision email; generate the certificate with
   the already-installed jsPDF.
8. **Respondent form friction:** 13 questions, *everything* mandatory including
   two free-text boxes, one long page, no progress indicator. Make the text
   questions optional and add a slim progress bar.
9. **Brand incoherence:** landing and thank-you pages say "National Staff
   Wellbeing Survey"; the product is the Human Kind Award; the accreditation
   framework — the differentiator — isn't mentioned on the landing page at all.

### Quick wins
- Fix the four `/new-survey` links (or add a redirect route).
- Getting Started checklist: derive completion from real data (a survey exists /
  was sent / has responses) instead of marking steps done on click
  (`GettingStartedGuide.tsx:44-53`).
- Rename the dashboard "Benchmark score" tile to "Avg. recommendation score".
- Thank-you page copy: school-facing brand + "your school sees anonymised results".
- Label the certificate button "coming soon" (or hide) until implemented.
- Nav: "Survey" → "Surveys"; consider "Improve" → "Action Plan".
- Analysis empty-state sentence vs. survey dropdown contents disagree — align.
- Interim toast fix for the publish flow ("Find your link on the Surveys page").
